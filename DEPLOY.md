# Deploying Kashmir Birds AI on Render (free tier)

## What is deployed

The Django site "Birds of Paradise" in `website/`. The live site is
**read-only in practice**: it serves the committed SQLite snapshot
(`website/db.sqlite3`) and the committed bird photos
(`website/media/birds/`). Anything written at runtime (admin edits,
uploaded images) is lost when Render restarts or redeploys the
service, because Render's filesystem is ephemeral and the committed
snapshot is restored.

## How to deploy (dashboard steps)

1. Sign in to [Render](https://dashboard.render.com) (GitHub sign-in
   works) and create a **New Web Service**.
2. Connect the repo **YawerNazir123/kashmir-birds-ai**, branch `main`.
   Or use the Blueprint in `render.yaml`: Dashboard -> New ->
   Blueprint, point it at this repo.
3. Render reads `render.yaml`: root directory `website/`, build
   command installs requirements, runs `collectstatic` and `migrate`,
   start command runs Gunicorn.
4. Environment variables (set in the Render dashboard if not using
   the Blueprint, which sets them from `render.yaml`):
   - `SECRET_KEY` — generated by Render (`generateValue: true` in
     `render.yaml`). Never reuse the old key that was committed in
     `settings.py` before this change; treat it as compromised.
   - `DEBUG` — `False`
   - No `DATABASE_URL` — see below.
5. Deploy. First build clones the whole repo (see "Repo size" below),
   so expect it to take several minutes. Then open the
   `https://kashmir-birds-ai.onrender.com` URL (name may differ) and
   check: landing page counts, gallery search, a bird detail page
   with its photo, and that static CSS loads.
6. Free-tier note: the free web service spins down after inactivity,
   so the first visit after idle can take ~30-60 seconds to wake up.

## SQLite vs Postgres — decision

**SQLite (committed snapshot) for now.** Reasoning:

- The site is a read-only field guide: no user accounts, no
  user-generated content, and the only writes are admin edits.
- A Postgres database would only help if writes had to persist, but
  the bird photos would still be a problem: `import_birds` copies
  photos into `website/media/` on the local filesystem, which is
  ephemeral on Render, so photos imported at runtime would vanish
  on restart even with Postgres. Fixing that properly needs object
  storage (S3/Cloudinary) for media, not just a different database.
- Render's free Postgres is time-limited (it expires), so it would
  add a future migration chore for no benefit today.
- The committed `db.sqlite3` (1.3 MB) and committed media photos
  already contain the fully imported, corrected data, so the site
  works with zero import step on Render.

**Upgrade path, when writes or uploads matter:** add a Render
Postgres database, set `DATABASE_URL` (settings.py picks it up
automatically via `dj-database-url`), run
`python manage.py migrate` and then `python manage.py import_birds`
once from a machine with the repo checked out (it reads
`../bird_database` relative to `website/`), and move media to
object storage. Do not run `import_birds` in the Render build.

## Repo size — risk

The repo is ~1.56 GiB (initial push: 5,653 objects), almost all of
it bird photos in `bird_database/` (724 folders) and
`website/media/birds/`. Render clones the full repo on every deploy,
so builds are slow and a build could time out on the free tier. The
first deploy is the test: if the clone/build times out, the fix is
to move `bird_database/` photos out of the deployed repo (e.g. keep
them in a separate data repo or object storage) — not to shrink the
site itself.

## Files added for deployment

- `render.yaml` — Render Blueprint (free web service).
- `website/requirements.txt` — Django 6.0.5 (the version the
  project was generated with), Gunicorn, WhiteNoise, Pillow,
  `dj-database-url`, `psycopg[binary]`.
- `website/runtime.txt` — Python 3.13.0.
- `website/website/settings.py` — `SECRET_KEY`/`DEBUG`/
  `ALLOWED_HOSTS` from environment, WhiteNoise for static files,
  optional `DATABASE_URL` override, proxy SSL header.
- `website/website/urls.py` — serves `/media/` in production too
  (Django static view; acceptable for this small free-tier site).
- `.gitignore` — adds `.env`, `staticfiles/`, `*.log`. It
  deliberately does **not** ignore `db.sqlite3` or `media/`.

## Known limitations (not fixed by this deploy)

- The "AI Identify" page is a stub: it ignores the uploaded photo
  and always returns the first bird in the database.
- Admin edits and uploads do not persist across restarts/redeploys.
- The old committed `SECRET_KEY` is public in git history; rotating
  it here only protects the new deployment. The key in history
  cannot be un-published without rewriting history.
