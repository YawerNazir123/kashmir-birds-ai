# Deploying Kashmir Birds AI on Render (free tier)

## What is deployed

The Django site "Birds of Paradise" in `website/`. The live site is
https://www.birdsofparadise.in (and
https://kashmir-birds-ai.onrender.com).

- **Database:** Neon Postgres, project "birds-of-paradise", via
  `DATABASE_URL` set in the Render dashboard. User accounts and
  Contact form messages live there and survive restarts and
  redeploys. There is no committed SQLite snapshot and no
  `website/media/birds/` photos in the repo.
- **Bird data:** 745 species, from `bird_database/<folder>/info.json`
  (745 folders). The build runs `import_birds` on every deploy to
  refresh every record in place, then `sync_local_names` as a safety
  net for the local names.
- **Photos:** served from the repo's `bird_database/` via
  `/bird-images/` (see `website/website/urls.py`). Nothing is copied
  into `media/` at build time. `/media/` only serves legacy image
  paths stored as `birds/...` in the database.
- **AI Identify:** a real model, not a stub. A ConvNeXt-Small ONNX
  classifier for 707 species (test top-1 66.38% / top-5 84.57%),
  served by ONNX Runtime. The two model files (1.2 MB graph,
  200 MB weights) are downloaded at build time from the public
  Hugging Face repo `yawarnazir/kashmir-birds-v2-onnx` at a pinned
  revision, with a SHA-256 check on each file (see
  `birds/identifier.py` and the `download_model` command). If the
  download fails, the deploy still goes ahead and the site fetches
  the model at runtime in a background thread.
- **Login:** email + password only (no Google OAuth, no phone OTP).
  Brute-force protection comes from django-axes: 5 failed attempts
  from one IP lock it out for 1 hour, on both `/login/` and
  `/admin/`.
- **Public pages:** landing, birds database, gallery, every bird
  detail page, About, Contact, `/sitemap.xml` and `/robots.txt`.
  AI Identify and account pages need a signed-in user. Unknown
  paths return a real 404.

## How to deploy (dashboard steps)

1. Sign in to [Render](https://dashboard.render.com) (GitHub sign-in
   works) and open the existing **kashmir-birds-ai** web service.
   Or use the Blueprint in `render.yaml`: Dashboard -> New ->
   Blueprint, point it at this repo.
2. Connect the repo **YawerNazir123/kashmir-birds-ai**, branch `main`.
3. Render reads `render.yaml`: root directory `website/`, build
   command installs requirements, runs `collectstatic` and `migrate`,
   then `import_birds`, `sync_local_names` and `download_model`;
   start command runs Gunicorn with one worker.
4. Environment variables (set in the Render dashboard):
   - `SECRET_KEY` — generated by Render (`generateValue: true` in
     `render.yaml`). Never reuse the old key that was committed in
     `settings.py` before this change; treat it as compromised.
   - `DEBUG` — `False`
   - `DATABASE_URL` — the Neon Postgres connection string, set in the
     dashboard. **Do NOT declare a database in `render.yaml`:** that
     would point the live site at a fresh empty database and lose all
     user accounts and contact messages. If the service is ever
     recreated, re-attach the same `DATABASE_URL` in the dashboard.
   - `PYTHON_VERSION` — `3.12.0` (set in `render.yaml`; Render
     defaults to 3.14, which psycopg-binary 3.2.1 has no version
     for). There is no `runtime.txt`.
5. Deploy. First build clones the whole repo (see "Repo size" below),
   so expect it to take several minutes. Then open the live URL and
   check: landing page counts, gallery search, a bird detail page
   with its photo, and that static CSS loads.
6. Free-tier note: the free web service spins down after inactivity,
   so the first visit after idle can take ~30-60 seconds to wake up.
   A keep-awake ping hits the homepage every 10 minutes so Googlebot
   can fetch the site.

## Repo size — risk

The repo is about 1.4 GB, almost all of it bird photos in
`bird_database/` (745 folders). Render clones the full repo on every
deploy, so builds are slow and a build could time out on the free
tier. If that happens, the fix is to move `bird_database/` photos
out of the deployed repo (e.g. keep them in a separate data repo or
object storage) — not to shrink the site itself.

## Files used for deployment

- `render.yaml` — Render Blueprint (free web service).
- `website/requirements.txt` — Django 6.0.5 (the version the
  project was generated with), Gunicorn, WhiteNoise, Pillow,
  `dj-database-url`, `psycopg[binary]`, django-axes, django-ipware.
- `website/website/settings.py` — `SECRET_KEY`/`DEBUG`/
  `ALLOWED_HOSTS` from environment, WhiteNoise for static files,
  `DATABASE_URL` override, proxy SSL header, HSTS and secure
  cookies, django-axes lockout settings.
- `website/website/urls.py` — serves `/media/` and `/bird-images/`
  in production too (Django static view with a long Cache-Control;
  acceptable for this small free-tier site).
- `.gitignore` — ignores `.env`, `staticfiles/`, `*.log`,
  `db.sqlite3` and `website/media/` (neither is committed).

## Known limitations (not fixed by this deploy)

- The old committed `SECRET_KEY` is public in git history; rotating
  it here only protects the new deployment. The key in history
  cannot be un-published without rewriting history.
- Content-Security-Policy is Report-Only, not enforcing: the login
  and identify pages use inline scripts and styles, which an
  enforcing policy would break. See `birds/middleware.py`.
- 45 of the 745 birds have no photo yet, and some photos are
  uncompressed originals of several MB. See the audit notes in the
  project workspace for the remaining data work.
